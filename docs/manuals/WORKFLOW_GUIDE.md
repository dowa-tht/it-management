# 📖 คู่มือระบบ Workflow (Unified Workflow Guide)

คู่มือนี้อธิบายขั้นตอนการทำงานของระบบตั้งแต่กระบวนการเข้าใช้งาน การลงทะเบียนยืนยันตัวตน (Login, Gatekeeper, Onboarding) ไปจนถึงกระบวนการอนุมัติเอกสารแบบละเอียด (Incident & Checklist)

---

## 🛡️ 1. ขั้นตอนการทำงานของ Login, Gatekeeper และ Onboarding (Identity & Access Flow)

เพื่อให้ระบบรักษาความปลอดภัยเป็นไปตามมาตรฐานสูงสุดและป้องกันการเข้าถึงข้อมูลโดยไม่ผ่านกระบวนการลงทะเบียน (Loop Prevention) ระบบจึงออกแบบ Flow การยืนยันตัวตนและการตรวจสอบสิทธิ์เข้าใช้งานร่วมกันดังนี้:

### 1.1 การเข้าสู่ระบบแบบรวมศูนย์ (Unified Login & Microsoft SSO)
1. **ทางเลือกการเข้าระบบ:** รองรับทั้งรหัสผ่านธรรมดาและ Microsoft OAuth (SSO) ผ่าน Azure AD
2. **การคัดกรองทะเบียนขาว (Whitelist Check):** ทุกการล็อกอินจะนำ email ไปแปลงเป็น SHA-256 Hash เพื่อนำไปค้นหาในตาราง `user_whitelist`
   - *ไม่ผ่านการทะเบียนขาว (Not Whitelisted):* ระบบจะยกเลิก Session ทันที (Purge session) และส่งไปหน้า `/access-denied`
   - *ผ่านการทะเบียนขาว (Whitelisted):* บันทึก Log ลง `login_logs` และเข้าสู่ขั้นถัดไป

### 1.2 ผู้พิทักษ์ด่านหน้าระดับโกลบอล (Global Gatekeeper - Middleware Proxy Layer)
1. **หน้าที่:** ดักจับทราฟฟิกเฉพาะการเข้าถึงหน้า `/dashboard*`
2. **กลไกการทำงาน:**
   - ตรวจสอบ Cookie `dowa_onboarded`
     - หากเป็น `'true'` จะอนุญาตให้เข้าผ่านโดยไม่ติดโหลดเพิ่ม (NextResponse.next())
     - หากไม่มี Cookie หรือเป็นค่าอื่น จะส่งคำสั่ง Query ไปตรวจสอบในฐานข้อมูล `user_profiles`
       - หาก `is_onboarded === true` -> ตั้งค่า Cookie `dowa_onboarded = 'true'` (อายุ 7 วัน) และให้ผ่าน
       - หาก `is_onboarded === false` -> ส่งการทำงานไปยัง `/api/onboarding/init` เพื่อเริ่มกระบวนการลงทะเบียน

### 1.3 กระบวนการลงทะเบียนใช้งานครั้งแรก (Onboarding Flow)
1. **การสร้าง Token (Self-healing):** 
   - ระบบจะสร้าง `onboarding_token` (UUIDv4) มีอายุ 24 ชั่วโมง บันทึกลงตาราง `user_profiles` แล้วส่งต่อไปที่ `/onboarding?token=...`
2. **ขั้นตอนภายในหน้าจอ Onboarding (`app/onboarding/page.js`):**
   - **Step 1 (Welcome):** แสดงข้อมูลพนักงานและเริ่มการตั้งค่า
   - **Step 2 (Password):** บังคับเปลี่ยนรหัสผ่านตามความซับซ้อนของ IT Audit (มีตัวเล็ก, ตัวใหญ่, ตัวเลข, อักขระพิเศษ, ยาว >= 8)
   - **Step 3 (PIN Setup):** ตั้งค่ารหัสผ่านเซ็นเอกสาร (Signature PIN) 6 หลัก โดยจะทำหน้าที่แปลงเป็น Bcrypt Hash และบันทึกลงฟิลด์ `signature_pin` พร้อมสลับ `is_onboarded = true`, `onboarding_token = null` ในฐานข้อมูล และตั้ง Cookie `dowa_onboarded = 'true'`
   - **Step 4 (Link SSO):** บังคับ/แนะนำการเชื่อมโยงบัญชี Microsoft Account ผ่าน Azure OAuth เพื่อการล็อกอินครั้งถัดไป
   - **Step 5 (Success):** แจ้งเตือนเสร็จสิ้นกระบวนการเพื่อให้เข้าสู่ระบบด้วยข้อมูลใหม่

## 📊 2. ขั้นตอนการทำงานของหน้าจอ Dashboard ในแต่ละ Role (Dashboard Role Flow)

หน้าจอ Dashboard ทำหน้าที่สรุปสถานะ ความคืบหน้า และประเมินตัวชี้วัดประสิทธิภาพ (SLA) โดยแบ่งการทำงานและการแสดงผลออกตามบทบาทของผู้ใช้งานเป็น 2 กลุ่มหลักดังนี้:

### 2.1 หน้าจอสำหรับพนักงานทั่วไป (Employee Dashboard - สำหรับ Role `employee`)
1. **การคัดกรองข้อมูล:** ดึงข้อมูลและสถิติจากฐานข้อมูลเฉพาะกรณีการแจ้งซ่อม (`incidents`) ที่พนักงานท่านนั้นเป็นผู้รายงาน หรือเป็นผู้ได้รับมอบหมายงานเท่านั้น
2. **การแสดงผลสถิติและข้อมูล:**
   - การ์ดสถิติ 5 ช่อง: รายการทั้งหมด, รอดำเนินการ (Open), กำลังดำเนินการ (In Progress), รอฉันยืนยัน (Pending Approval), และเสร็จสมบูรณ์ (Closed)
   - กราฟแนวโน้มปัญหา (Trend Chart): แสดงสถิติการแจ้งปัญหาของตนเองย้อนหลัง 6 เดือน
   - สรุปประเภทปัญหา (Category Breakdown): แสดง Pie Chart ของระบบที่ได้รับผลกระทบสูงสุด 5 อันดับแรก (Top 5 Affected Systems)
   - รายการล่าสุด: แสดงรายการแจ้งซ่อมของตนเอง 5 รายการล่าสุดเพื่อติดตามความคืบหน้า
3. **การเข้าถึงฟังก์ชัน:** มีปุ่มทางลัดด่วนเพื่อกดแจ้งปัญหาไอทีใหม่ (+ แจ้งเรื่องใหม่) เชื่อมไปยังหน้า `/dashboard/incidents/new`

### 2.2 หน้าจอสำหรับเจ้าหน้าที่ ผู้บริหาร และผู้ตรวจสอบ (IT & Compliance Dashboard - สำหรับ Role อื่นๆ)
1. **การคัดกรองข้อมูล:** โหลดข้อมูลทั้งหมดของระบบ (Incidents ทั้งหมด, Checklist ทั้งหมด, Backup Logs ทั้งหมด) ย้อนหลัง 30-35 วันเพื่อประเมินความสอดคล้องเชิงระบบ
2. **การแสดงผลสถิติและข้อมูล:**
   - การ์ดสถิติรวมของระบบ: Checklist NG (ความผิดปกติที่พบ), เคส Incident ในรอบ 30 วัน, เคสที่มีระดับความรุนแรงสูง (High Severity), และจำนวนเคสตามสถานะ (Open, In Progress, Pending)
   - **IT Checklist Compliance:** แสดงสถานะการตรวจเช็คระบบ 7 วันทำการล่าสุดเป็นแถบสี (Streak) และระบุสถานะรายช่วงเวลา (Daily, Weekly, Monthly, Yearly)
   - **SLA Compliance Rate (30D):** แสดงสถิติเปอร์เซ็นต์การปิดงานตามเป้าหมาย SLA ในรอบ 30 วันล่าสุด โดยใช้รหัสสีแจ้งเตือนความเสี่ยง (เขียว >= 95%, เหลือง >= 90%, แดง < 90%)
   - กราฟแท่งแสดงจำนวน Incident 7 วันล่าสุด และ Pie Chart แสดงสัดส่วนตามระดับความรุนแรง
   - ตาราง SLA Tracking สำหรับเคสล่าสุด

### 2.3 ขั้นตอนการประมวลผลและการไหลของข้อมูล (Data Flow & Logic Steps)
1. **Trigger:** ผู้ใช้เข้าสู่ระบบและเปิดหน้าจอ `/dashboard`
2. **Inputs & Context Setup:**
   - เรียก Server Action `getDashboardData` โดยส่งค่า `timezoneOffset` เพื่อคำนวณวันปัจจุบัน (Today) ให้ตรงตามเขตเวลาจริง
   - เรียก `getCurrentUserSession` เพื่อยืนยันสิทธิ์และอีเมลของผู้ใช้
3. **Decision & Routing:**
   - หากผู้ใช้มี Role เป็น `employee` -> ประมวลผลและส่งคืนข้อมูลในกลุ่ม `employeeStats` และ `myRecentIncidents` เพื่อเรนเดอร์หน้าจอพนักงานทั่วไป
   - หากผู้ใช้มี Role อื่นๆ -> ทำการรัน Logic คำนวณสรุป Checklist Streak และคำนวณประเมินเวลา SLA ของเคสที่เปิดอยู่ (โดยการนำเวลาสร้างมาหักลบกับวันหยุดนักขัตฤกษ์/วันหยุดสุดสัปดาห์ และ Exclusion Pauses ตามจริง) เพื่อเรนเดอร์หน้าจอผู้ดูแลระบบ/ผู้ตรวจสอบ
4. **Polling & Refresh:**
   - ระบบหน้าบ้าน (Client) จะทำการ Poll อัปเดตข้อมูลใหม่จากหลังบ้านทุก ๆ 5 นาทีโดยอัตโนมัติ

## 🛠️ 3. ขั้นตอนการทำงานของฟังก์ชัน Incident & Incident[id] (Incident Detail & Actions Flow)

ระบบ Incident (ใบแจ้งซ่อม) และหน้ารายละเอียด Incident รายตั๋ว (`/dashboard/incidents/[id]`) ถูกควบคุมด้วยเงื่อนไขความปลอดภัยและกระบวนการอนุมัติแบบเป็นขั้นเป็นตอนตามแต่ละบทบาทผู้ใช้งานดังนี้:

### 3.1 การตรวจสอบสิทธิ์และปุ่มการทำงานตามบทบาท (Action Matrix by Role)
*   **Administrator (แอดมิน):** 
    *   แก้ไขฟิลด์ข้อมูลพื้นฐานของเอกสาร (Title, Severity, Affected System, Category)
    *   กรณีเคสอยู่ในสถานะ `Open` สามารถมอบหมายงาน (Dispatch) ให้กับเจ้าหน้าที่ IT Staff โดยเลือกรายชื่อ
    *   เพิ่ม/แก้ไข/ลบช่วงการหยุดนับเวลาชั่วคราว (SLA Exclusion) ด้วยตนเอง
    *   ยกเลิกเคส (Cancel Incident) โดยการเซ็นและยืนยันด้วย PIN ของตนเอง
*   **IT Staff (เจ้าหน้าที่เทคนิค):**
    *   กรณีเคสอยู่ในสถานะ `Open` สามารถกดรับเรื่องเข้าดำเนินการด้วยตนเอง (Acknowledge)
    *   เพิ่ม/แก้ไข/ลบช่วงการหยุดนับเวลาชั่วคราว (SLA Exclusion) เช่น กรณีรออะไหล่ หรือรอข้อมูลจากผู้ใช้งาน
    *   ส่งงานเพื่อปิดเคส (Resolve) โดยกรอกสาเหตุ แนวทางการแก้ไข และเซ็นชื่อยืนยันคู่กับผู้แจ้งเรื่อง
*   **Employee (พนักงานผู้แจ้งเรื่อง):**
    *   เปิดดูความคืบหน้าของตั๋วที่ตนเองเปิดไว้
    *   เซ็นยืนยันการ Resolve ในแท็บเล็ตของ IT (Remote Sign) โดยต้องผ่านการกรอก PIN 6 หลักของตนเอง หรือยืนยันรหัส OTP ทางอีเมล (กรณีผู้แจ้งภายนอกที่ไม่มีบัญชีในระบบ)
    *   ขอยกเลิกตั๋วของตนเอง (Cancel Incident) โดยยืนยันด้วย OTP ทางอีเมล
*   **Auditor (ผู้ตรวจสอบ):**
    *   เข้าชมข้อมูลตั๋ว สถิติ และระบบบันทึกเหตุการณ์ (Audit Logs) ทั้งหมดได้ในรูปแบบอ่านอย่างเดียว (Read-Only)

### 3.2 ขั้นตอนสำคัญในกระบวนการแจ้งซ่อม (Core Sub-Flows)

#### 1) การรับเรื่องและมอบหมายงาน (Acknowledge / Dispatch Flow)
*   **Trigger:** เจ้าหน้าที่กดปุ่ม **"Acknowledge / Dispatch"** บนหน้าจอ (สถานะตั๋วต้องเป็น `Open`)
*   **Inputs:** `severity` (Low, Medium, High), `assignee_id` (เฉพาะกรณี Admin มอบหมายให้ IT Staff)
*   **Conditional Branches:**
    *   *IT Staff กดรับเอง:* แสตมป์ชื่อ IT Staff คนนั้นเข้าเป็นผู้รับผิดชอบ (`assigned_to_id = actor.id`)
    *   *Admin กดมอบหมาย:* ตรวจสอบรายชื่อและมอบหมายให้ IT Staff ตามที่เลือก
*   **Outputs & DB Effects:** 
    *   เปลี่ยนสถานะตั๋วในตาราง `incidents` เป็น `In Progress`
    *   เริ่มการบันทึกสถิติ SLA (บันทึก `acknowledged_at` และ `assigned_at`)
    *   บันทึกประวัติการรับเรื่องลงตาราง System Audit Logs

#### 2) การแก้ไขปัญหาและส่งอนุมัติปิดตั๋ว (Resolve Flow)
*   **Trigger:** IT Staff กดปุ่ม **"Resolve"** ในหน้า Incident [id] (สถานะตั๋วต้องเป็น `In Progress`)
*   **Inputs:** คำอธิบายสาเหตุและแนวทางการแก้ปัญหา, รูปภาพและลายเซ็น IT/ผู้แจ้ง, รหัส PIN / OTP ยืนยันตัวตนของผู้แจ้ง
*   **Conditional Branches:**
    *   *ผู้แจ้งเป็นพนักงานภายใน:* ระบบตรวจสอบ Signature PIN 6 หลักของผู้แจ้งผ่าน `verifyEmployeePIN`
    *   *ผู้แจ้งเป็นพนักงานภายนอก:* ระบบส่งรหัส OTP 6 หลักไปยังอีเมลและรอการกรอกยืนยันบนหน้าจอ
    *   *การจัดลำดับ Workflow ตามระดับ Severity:*
        *   **High Severity:** ระบบสร้าง Workflow Step 3 ขั้นตอน: `IT Officer` -> `Reporter (ผู้แจ้ง)` -> `Manager (หัวหน้าแผนกไอที)`
        *   **Low / Medium Severity:** ระบบสร้าง Workflow Step 2 ขั้นตอน: `IT Officer` -> `Reporter (ผู้แจ้ง)`
*   **Outputs & DB Effects:**
    *   บันทึกข้อมูล `resolved_at`, `resolved_by` และคำอธิบายการแก้ปัญหาลงตาราง `incidents`
    *   สร้างขั้นตอนการอนุมัติในตาราง `document_approvals` ผ่านฟังก์ชัน `submitRequest`
    *   เปลี่ยนสถานะตั๋วเป็น `Pending Approval` (หรือสลับเป็น `Closed` ทันทีหากเงื่อนไข Workflow ครบถ้วน)
    *   หากยังมี approver ที่ต้องดำเนินการต่อ ระบบจะส่ง `Public Approval Link` ไปยัง approver ปัจจุบันทันที

#### 2.1) การอนุมัติผ่าน Public Approval Link
*   **Trigger:** ผู้อนุมัติเปิดลิงก์จากอีเมลที่ระบบส่งในช่วง `Pending Approval`
*   **Core Rules:**
    *   ลิงก์มีอายุ 15 นาที
    *   ลิงก์ 1 ชุดใช้ได้กับ browser session แรกที่เปิดเท่านั้น
    *   หากเปิดจาก session อื่น หรือ token ถูก consume/revoke ไปแล้ว ต้องให้ผู้ส่งเอกสารหรือ `admin` กด `Resend Approval Link`
*   **Screen Behavior:**
    *   หน้า public approve ต้องแสดงเลขเอกสาร, หัวข้อ, step ปัจจุบัน, เวลาหมดอายุ, และรายละเอียดการแก้ไขปัญหา (`Root Cause Analysis`, `Resolution`, `Corrective Action`)
    *   ผู้อนุมัติสามารถกรอก comment เพิ่มเติมแล้วกด `อนุมัติ` หรือ `ปฏิเสธ` ได้จากหน้าเดียว
*   **Security Controls:**
    *   ตรวจ token hash + expiry + revoke status
    *   ตรวจ one-time session cookie ที่ผูกกับการเปิดครั้งแรก
    *   เมื่อ action สำเร็จ ระบบจะ revoke token เดิม และหากมี step ถัดไปจะส่งอีเมลหา approver คนถัดไปอัตโนมัติ

#### 3) การขอยกเลิกตั๋ว (Cancel Flow)
*   **Trigger:** ผู้ใช้กดปุ่ม **"Cancel Incident"** ในหน้าจอ
*   **Inputs:** เหตุผลในการยกเลิก, รหัส PIN หรือ OTP ยืนยันตัวตน
*   **Conditional Branches (ตรวจสอบความปลอดภัยผ่าน `deriveIncidentCancelVerificationPolicy`):**
    *   *ผู้ใช้เป็น Admin/IT Staff:* บังคับกรอก **Signature PIN** ของตนเอง
    *   *ผู้ใช้เป็น Creator/Reporter (พนักงาน):* ส่งคำขอ **OTP** ไปยังอีเมลของผู้แจ้งและนำมากรอกยืนยันตัวตน
*   **Outputs & DB Effects:**
    *   สถานะตั๋วในตาราง `incidents` เปลี่ยนเป็น `Cancelled`
    *   ล้างสเต็ปรอการอนุมัติในตาราง `document_approvals` ทั้งหมดเป็น Cancelled ผ่าน `cancelDocument`

#### 4) การส่งลิงก์อนุมัติใหม่ (Resend Approval Link)
*   **ผู้ที่กดได้:** `sender` ของเอกสาร และ `admin` เท่านั้น
*   **สถานะที่กดได้:** เฉพาะตอน Incident ยังอยู่ใน `Pending Approval`
*   **ผลของการกด:**
    *   revoke ลิงก์เดิมของ step ปัจจุบัน
    *   ออก token ใหม่อายุ 15 นาที
    *   ส่งอีเมลใหม่ไปยัง approver คนเดิม
*   **หมายเหตุ:** ปุ่มนี้อยู่ในส่วน `Workflow Progress` ของหน้า Incident Detail

## 📈 4. ขั้นตอนการทำงานของฟังก์ชัน SLA Report (SLA Report Flow)

หน้าจอรายงานข้อตกลงการให้บริการ (SLA Report - `/dashboard/reports/sla`) ทำหน้าที่แสดงรายงานตัวชี้วัดประสิทธิภาพของตั๋วแจ้งซ่อม โดยใช้กลไกการประเมินเวลาทำการจริงและมีรายละเอียดทางเทคนิคดังนี้:

### 4.1 แหล่งที่มาของเกณฑ์และชั่วโมงทำงาน (Working Hours & SLA Targets)
*   **วันเวลาทำงาน (Working Hours):** อ้างอิงตาราง `system_settings` (คีย์ `working_hours`) โดยนับเฉพาะช่วงเวลาทำการ (เช่น จันทร์-ศุกร์ 08:30 - 17:30 น.)
*   **การยกเว้นวันหยุด (Holidays):** ข้ามการนับเวลาสำหรับวันเสาร์-อาทิตย์ และวันที่อยู่ในตารางวันหยุดนักขัตฤกษ์ (`holidays`)
*   **เกณฑ์เป้าหมายดัชนี (SLA Limits):** กำหนดระยะเวลานาฬิกาบริการสูงสุดแยกตามระดับความรุนแรง (Severity) ของตั๋ว:
    *   *High Severity:* Response ภายใน 60 นาที / Resolution ภายใน 240 นาที (4 ชั่วโมง)
    *   *Medium Severity:* Response ภายใน 120 นาที / Resolution ภายใน 480 นาที (8 ชั่วโมง)
    *   *Low Severity:* Response ภายใน 360 นาที / Resolution ภายใน 1620 นาที (3 วันทำการ)

### 4.2 ขั้นตอนการประมวลผลคำนวณสถิติและสถานะ (Evaluation Logic)
1.  **การดึงข้อมูล (Query Engine):** 
    *   ดึงตั๋ว `incidents` ในช่วงเวลาที่พนักงานเลือกกรอง โดยใช้ Supabase Admin Client เพื่อคำนวณข้อมูลย้อนหลัง 30 วัน
    *   ดึงตารางค่าตั้งค่าระบบ วันหยุดราชการ และ SLA Exclusion (`incident_exclusions`) ทั้งหมดของตั๋วเหล่านั้น
2.  **การคำนวณรายเคส (SLA Snapshot):**
    *   **Response SLA:** คำนวณเวลาสุทธิจาก `created_at` ไปยัง `acknowledged_at` (ชั่วโมงทำงานปกติ) เปรียบเทียบกับเป้าหมายความรุนแรง
    *   **Resolution SLA:** คำนวณเวลาสุทธิจาก `created_at` ไปยัง `resolved_at` (หักลบช่วงเวลาที่ระงับชั่วคราวใน `incident_exclusions`)
3.  **การหาค่าสถิติเฉลี่ยรวม (Overall Score):**
    *   นับเคสที่ผ่านเกณฑ์เวลาประเมินหาเปอร์เซ็นต์ Response และ Resolution
    *   ประเมินผลคะแนนความสอดคล้องรวม: `Compliance Rate = (Response Rate % + Resolution Rate %) / 2`

### 4.3 ระบบแคชและการแสดงผลหน้าจอ (Caching & UI Rendering)
*   **กลไก Cache Client-Side (SWR):** หน้ารายงานใช้ตัวแปรอ็อบเจกต์ `reportCache` เก็บข้อมูลการกรองโดยใช้คีย์เป็น `startDate-endDate-page` เพื่อให้เมื่อผู้ใช้กดย้อนกลับมาดูการกรองแบบเดิม ระบบจะแสดงข้อมูลที่โหลดไว้ก่อนหน้าทันทีโดยไม่ติดขัด (Zero flickering) และอัปเดตข้อมูลสดหลังบ้านทันที
*   **การ์ดสถิติไล่เฉดสี (Compliance Card Gradient):** การ์ด Compliance สรุปผลจะแสดงสีตามเกณฑ์ประสิทธิภาพ:
    *   🟢 **สีเขียว (Green >= 95%):** บรรลุเป้าหมายการให้บริการ (On Target)
    *   🟡 **สีเหลือง (Yellow >= 90%):** ต่ำกว่าเป้าหมายเล็กน้อย (Warning)
    *   🔴 **สีแดง (Red < 90%):** ต่ำกว่าเกณฑ์ที่ระบบยอมรับได้ (Below Target)

## 📋 5. ขั้นตอนการทำงานของฟังก์ชัน IT Checklist (IT Checklist Flow)

ระบบการตรวจเช็คงานไอทีประจำวัน (IT Checklist) และหน้ารายละเอียดรายการตรวจสอบ (`/dashboard/checklist/[id]`) ควบคุมสิทธิ์การกรอกข้อมูลและการพิจารณาอนุมัติผ่านสถานะและ Template หลากหลายประเภทดังนี้:

### 5.1 ประเภทและลักษณะพฤติกรรมของ Template (UI Template Types)
1. **Type 0 (General Template):**
   - การบันทึกผลตรวจสอบมาตรฐานทั่วไปในลักษณะการเลือกสถานะอย่างง่ายผ่านปุ่มตัวเลือก **OK / NG**
2. **Type 1 (Photo Evidence Template):**
   - **การแนบพิกัดตำแหน่ง (Optional GPS):** รองรับการดึงพิกัดผ่าน Web Geolocation API (สถานะ: `captured`, `denied`, `unsupported`, `timeout`, `error`)
   - **การจัดการขนาดและการบีบอัดรูปภาพ:** บีบอัดไฟล์ภาพผ่าน Canvas API โดยจำกัดความกว้างและสูงไม่เกิน 1,000px และบันทึกในรูปแบบไฟล์ JPEG ด้วยคุณภาพ 0.5 (ช่วยลดขนาดภาพได้มากกว่า 50% เหลือช่วง 50-80KB)
   - **ระบบลายน้ำ (Watermark):** วาดลายน้ำระบุหัวข้อ `"DOWA IT SYSTEM | วันที่และเวลาทำการ"` ทับลงบนรูปภาพพร้อมแสตมป์พิกัดพิกัด GPS ลงบนมุมภาพหากเปิดใช้งาน
   - **พื้นที่จัดเก็บข้อมูล (OneDrive Connection):** ส่งภาพที่ผ่านการเข้ารหัส Base64 ไปบันทึกที่โฟลเดอร์ `Apps/Dowa-IT-System/Evidence` ผ่าน OneDrive API และหากเป็นการอัปโหลดรูปภาพใหม่ทดแทนรูปภาพเดิม ระบบจะสั่งลบไฟล์ภาพเดิมใน OneDrive ออกโดยอัตโนมัติแบบ Asynchronous
3. **Type 2 (Procedure Plan Template):**
   - **ขั้นตอนการตรวจสอบย่อย (Sub-steps Checklist):** เจ้าหน้าที่สามารถกด Checkbox เพื่อดำเนินขั้นตอนการกู้คืนหรือตรวจเช็คย่อยเรียงลำดับ
   - **เกณฑ์การตรวจสอบ:** ต้องระบุ **ผลการประเมิน (OK/NG)** และ **ระยะเวลาการทำงาน (HH:mm)** ครบทุกขั้นตอนย่อยที่เลือกจึงจะถือว่ารายการนั้นสมบูรณ์ หากมีขั้นตอนใดถูกเลือกแต่กรอกข้อมูลไม่ครบถ้วน ระบบจะแสดงข้อความแจ้งเตือนสีเหลืองและบล็อกไม่ให้เจ้าหน้าที่ทำการบันทึกข้อมูลเอกสารหลักได้
   - **การสลับ Uncheck:** หากยกเลิกการเลือกขั้นตอนย่อย ระบบจะล้างค่าพฤติกรรม ผลประเมิน และระยะเวลาของขั้นตอนนั้นออกทันที
4. **Type 3 (Measure Template):**
   - รับข้อมูลเป็นตัวเลขเชิงปริมาณพร้อมแสดงเป้าหมายการประเมินต่ำสุด-สูงสุด (Min-Max Range Goal) และแจ้งเตือนหากผลลัพธ์หลุดจากขอบเขตที่ปลอดภัย
5. **Type 4 (Link Template):**
   - แสดงปุ่มสำหรับคลิกเปิดหน้าลิงก์ภายนอก (`OPEN LINK`) พร้อมตัวเลือกบังคับระบุหมายเหตุ
6. **Type 5 (Signoff Template):**
   - ลำดับปุ่มกดลายเซ็นแยกตามบทบาทที่กำหนดเพื่อปิดรอบการรับผิดชอบ

### 5.2 การควบคุมเวลาและสถานะเอกสาร (Time Tracking & State Flow)
1. **เวลาเริ่มต้น (Start Time):** เจ้าหน้าที่ระบุรูปแบบวันที่และเวลาในการปฏิบัติงานด้วยรูปแบบ `DD/MMM/YYYY HH:mm` (เช่น `25/May/2026 14:30`) ระบบจะบันทึกเข้าสู่ฟิลด์ `start_time` ในฐานข้อมูลพร้อมระบบบันทึกเหตุการณ์ Audit Logs
2. **ระยะเวลารวม (Total Duration):** คำนวณอัตโนมัติจากผลรวมของระยะเวลาที่ใช้ปฏิบัติงานของหัวข้อตรวจสอบย่อยทั้งหมด
3. **เวลาสิ้นสุด (Calculated End Time):** คำนวณแบบพลวัต (Dynamic) โดยการนำวันเวลาเริ่มต้นรวมเข้ากับระยะเวลารวมในการตรวจเช็คทั้งหมด
4. **การคำนวณสัดส่วนความคืบหน้า (Progress Calculation):** นับสัดส่วนความคืบหน้าการทำงานเป็นเปอร์เซ็นต์ (0 - 100%) โดยคำนวณจากจำนวนหัวข้อการตรวจสอบที่บันทึกสถานะเรียบร้อยเทียบกับหัวข้อตรวจสอบทั้งหมด

### 5.3 เงื่อนไขและกฎการบันทึกข้อมูล (Validation & Blocker Matrix)
1. **การบันทึกผลตรวจสอบล้มเหลว (NG Constraint):**
   - หากตรวจพบรายการสถานะเป็น **NG** และบันทึกรายละเอียดปัญหาแล้ว ระบบจะบังคับให้เจ้าหน้าที่เปิดตั๋ว Incident เพื่อผูกข้อมูลการแก้ไขปัญหาไอทีผ่าน `ref_type = 'checklist'` และ `ref_id` เสมอ
   - ระบบจะป้องกันไม่ให้ดำเนินการส่งอนุมัติเอกสารหลักหากพบจุดที่เป็น **NG** แต่ยังไม่มีการเปิดเคสแจ้งซ่อม (Incident Case) รองรับ
2. **ผลการประเมินภาพรวมระดับเอกสาร (Final Document Evaluation):**
   - เมื่อสัดส่วนความคืบหน้าครบ 100% แล้ว ระบบจะแสดงการ์ดสำหรับทำประเมินเอกสารภาพรวม (`evaluation_result` = OK หรือ NG)
   - หากเลือกประเมินเอกสารภาพรวมเป็น **NG** ระบบจะบังคับให้กรอกรายละเอียดข้อบกพร่อง/หมายเหตุภาพรวมลงในฟิลด์ `evaluation_remark` (ห้ามว่าง) ก่อนส่งอนุมัติเอกสาร

### 5.4 การยืนยันสิทธิ์และการพิจารณาอนุมัติ (Approval & Security Mode)
1. **การอนุมัติภายในระบบของตนเอง (Direct Sign):** เจ้าของสิทธิ์ล็อกอินอยู่บนอุปกรณ์ตนเอง สามารถเซ็นชื่อและส่งอนุมัติได้ทันทีโดยไม่ต้องระบุรหัส PIN
2. **การเซ็นอนุมัติระยะไกล (Remote PIN Signatures):**
   - กรณีรันเอกสารผ่านอุปกรณ์เครื่องอื่น ผู้มีสิทธิ์อนุมัติต้องกรอก **Signature PIN 6 หลัก** เพื่อถอดถอนและลงลายมือชื่อแทน
   - การอนุมัติระยะไกลสำหรับเอกสารกลุ่ม IT Checklist ถูกจำกัดเฉพาะผู้ใช้งานที่มีสถานะ Role เป็น `admin` และ `it_staff` เท่านั้น
3. **การส่งเรื่อง/การตีกลับและเริ่มเอกสารใหม่ (Action States):**
   - **Submit:** ล็อคการแก้ไขของเจ้าหน้าที่และส่งเข้าสู่ตารางอนุมัติ (`document_approvals`)
   - **Reject:** ล้างลายเซ็นและตีกลับสถานะเอกสารไปที่ `Open` (ร่าง) เพื่อให้แก้ไขประเด็นที่บกพร่องใหม่
   - **Reopen:** ล้างลายเซ็นผู้อนุมัติเดิมออกทั้งหมดและดึงเอกสารกลับมาสู่สถานะแก้ไขใหม่ (สิทธิ์เฉพาะ `admin` หรือ `it_staff`)
   - **Cancel:** ล้างคิวรอการอนุมัติและระบุสถานะเป็น `Cancelled` โดยต้องยืนยันตัวตนด้วย PIN/OTP (สิทธิ์เฉพาะ `admin` หรือเจ้าของเอกสาร)

## 💾 6. ขั้นตอนการทำงานของฟังก์ชัน Backup Logs (Backup Logs Flow)

หน้าจอประวัติการสำรองข้อมูล (Backup Log - `/dashboard/backup`) ทำหน้าที่บันทึกและประเมินผลประสิทธิภาพการสำรองข้อมูลเซิร์ฟเวอร์และระบบปฏิบัติการประจำวัน โดยใช้โครงสร้างข้อมูลแบบเดี่ยวและมีกระบวนการดังนี้:

### 6.1 สิทธิ์การใช้งานและการกรอกข้อมูล (Access & Form Validation)
*   **การกรองสิทธิ์ (Read-Only Restriction):** 
    *   ผู้ใช้ทั่วไปและ IT Staff สามารถดูประวัติ บันทึกข้อมูล และลบแถวข้อมูลของตนเองได้
    *   ผู้เข้าเยี่ยมชม (`visitor`) จะไม่ปรากฏปุ่ม "+ บันทึก Backup" และปุ่มลบ (×) บนหน้าตารางข้อมูล (ดูได้อย่างเดียว)
*   **ระบบที่รองรับการ Backup (System Name):**
    1. `Server & File Share` (ระบบเซิร์ฟเวอร์หลักและการแชร์ไฟล์)
    2. `Microsoft 365` (ระบบอีเมลและคลาวด์องค์กร)
*   **สถานะผลการทำงาน (Backup Status):**
    *   `Success` (สำเร็จ - สีเขียว)
    *   `Failed` (ล้มเหลว - สีแดง)
    *   `No Backup Task` (ไม่มีงานสำรองในวันนั้น - สีเทา)
*   **กฎการ Validation (ห้ามบันทึกซ้ำซ้อน):**
    *   ระบบป้องกันไม่ให้เพิ่มบันทึกที่มี `log_date` (วันที่) และ `system_name` (ชื่อระบบ) ซ้ำกันกับแถวเดิมที่มีในฐานข้อมูล โดย 1 ระบบสามารถบันทึกประวัติการ Backup ได้สูงสุดเพียง 1 ครั้งต่อวันทำการ

### 6.2 ขั้นตอนสำคัญในการทำงาน (Backup Sub-Flows)

#### 1) การดึงประวัติและการคำนวณอัตราความสำเร็จ (Fetch & Calculate Stats Flow)
*   **Trigger:** ผู้ใช้เปิดหน้าจอหรือสลับฟิลเตอร์วันที่ (วันนี้, 7 วัน, 30 วัน, เดือนนี้, 3 เดือน, ปีนี้)
*   **Inputs:** วันเวลาช่วงเริ่มต้นที่คำนวณจากประเภทฟิลเตอร์
*   **Conditional Branches:**
    *   *มี Cache ท้องถิ่น (SWR):* นำประวัติในหน่วยความจำขึ้นแสดงบนหน้าจอทันทีเพื่อลดรอยต่อ
    *   *ไม่มี Cache หรือ Revalidate:* ส่งคำขอคิวรีไปยังตาราง `backup_logs` ของ Supabase
*   **Outputs & DB Effects:**
    *   คำนวณและแสดงผลการ์ดสถิติ 4 ใบ: รายการทั้งหมด, สำเร็จ (Success), ล้มเหลว (Failed), อัตราความสำเร็จ (Success Rate %)
    *   *สูตรอัตราความสำเร็จ:* `(จำนวนตั๋ว Success / จำนวนตั๋วทั้งหมด) * 100`

#### 2) การบันทึกผลการสำรองข้อมูล (Add Backup Log Flow)
*   **Trigger:** พนักงานกรอกรายละเอียดในฟอร์มและกดปุ่ม **"บันทึก"**
*   **Inputs:** วันที่บันทึก, ระบบ, สถานะ, หมายเหตุเพิ่มเติม
*   **Validation Check:**
    *   ค้นหาในตาราง `backup_logs` ด้วยวันที่และระบบที่กำลังบันทึก หากพบข้อมูลเดิมระบบจะแจ้งเตือน (Alert) และยกเลิกการดำเนินงาน
*   **Outputs & DB Effects:**
    *   เพิ่มแถวข้อมูลประวัติการบันทึกใหม่ลงในตาราง `backup_logs`
    *   สั่งรีเฟรชอัปเดตข้อมูลตารางหน้าจอ และล้างค่าแบบฟอร์มเพื่อเตรียมพร้อมบันทึกรายการถัดไป

#### 3) การลบประวัติการบันทึก (Delete Log Flow)
*   **Trigger:** พนักงานคลิกปุ่มกากบาท **"×"** ท้ายรายการที่ต้องการลบ
*   **Inputs:** ไอดีแถวข้อมูล (`id`)
*   **Outputs & DB Effects:**
    *   แสดงกล่องข้อความยืนยันการลบตั๋ว (Confirm Dialogue)
    *   ทำการ Delete แถวข้อมูลในตาราง `backup_logs` ตามไอดีที่อ้างอิง
    *   สั่งรีเฟรชประวัติข้อมูลบนหน้าจอ

## ⚙️ 7. ขั้นตอนการทำงานของฟังก์ชัน System Setup (System Setup Flow)

ระบบการตั้งค่าระบบไอทีส่วนกลาง (System Setup) ทำหน้าที่เป็นฐานข้อมูลพื้นฐานของระบบการทำงานทั้งหมด โดยแบ่งออกเป็น 4 หน้าจอย่อยที่สำคัญดังนี้:

### 7.1 การจัดการเลขรันเอกสาร (No. Series Management)
1. **โครงสร้างข้อมูลและพฤติกรรม (Header & Lines Structure):**
   - **Header (`no_series`):** เก็บข้อมูลรหัสหลัก (เช่น `INC` สำหรับ Incident, `CHK` สำหรับ Checklist) และรูปแบบรหัส เช่น `DTT-INC-YYMM-###`
   - **Lines (`no_series_lines`):** เก็บรายละเอียดข้อมูลการนับจริงตามช่วงเวลา โดยระบุ `starting_date` เพื่อทำการเริ่มนับเลขใหม่เมื่อขึ้นรอบเวลาตามกำหนด (เช่น รายเดือน)
2. **การรันเลขถัดไปแบบพลวัต (Next Number Preview):**
   - คำนวณโดยดึงข้อมูลรายละเอียดในตาราง `no_series_lines` ที่มี `starting_date` น้อยกว่าหรือเท่ากับวันปฏิบัติงานจริง (`workingDate` ที่ระบุในระบบ)
   - ดึงค่า `last_no_used` ล่าสุดที่ถูกบันทึกไปแล้วมาคำนวณบวก 1 และแทนค่าลงในรูปแบบ Format (YY = ปี ค.ศ., MM = เดือน 2 หลัก, ### = จำนวนหลักตัวเลขรัน)
3. **การนำเข้าข้อมูลและการสำรองข้อมูล (CSV Data Flow):**
   - **Download Template:** ส่งออกเทมเพลตมาตรฐานระบุคอลัมน์ `code`, `format`, `starting_date`, และ `last_no_used`
   - **Import CSV:** 
     - ตรวจสอบคอลัมน์ของไฟล์นำเข้า หากโครงสร้างคอลัมน์ไม่ครบถ้วนจะทำการยกเลิก
     - หากโครงสร้างครบถ้วน ระบบจะตรวจสอบกับข้อมูลตาราง `no_series` ก่อนเพื่อสร้าง Header (หากไม่มีอยู่) จากนั้นจะนำข้อมูลลงไปบันทึก (Insert/Update) ในตาราง `no_series_lines`
     - แสดงผลสรุปจำนวนความสำเร็จและความผิดพลาดผ่านแถบข้อความแจ้งเตือน

### 7.2 กำหนดเวลาทำงานหลักขององค์กร (Working Hours)
1. **เวลาเริ่มและเลิกงานปกติ (Start & End Time Window):**
   - บันทึกรูปแบบเวลาเป็น String ในฐานข้อมูล (เช่น `08:30` - `17:30`) นำไปแปลงค่าคำนวณ Business Minutes ต่อวัน (หักเวลาทำการปกติ)
2. **วันทำงานประจำสัปดาห์ (Working Days):**
   - เก็บค่าอาร์เรย์วันทำการ เช่น `[1, 2, 3, 4, 5]` (จันทร์ - ศุกร์) เพื่อกำหนดวันที่จะนำไปนับระยะเวลาทำงานจริง
3. **ผลลัพธ์การบันทึกตั้งค่า:**
   - ทำการ Upsert ข้อมูลการตั้งค่าลงตาราง `system_settings` คีย์ `working_hours` และอ้างอิงช่วงเวลาทำงานนี้ไปใช้คำนวณ Business Minutes ของ Incident ทั้งหน้า Incident Detail, หน้า Dashboard และ SLA Reports ทันที
   - บันทึกประวัติการแก้ไขข้อมูลด้วย Audit log (`recordClientAuditLog`) โดยระบุข้อมูลก่อนและหลังการบันทึก

### 7.3 ปฏิทินวันหยุดประจำปี (Holidays Calendar)
1. **การตั้งค่าวันหยุดประจำปี:**
   - บันทึกประวัติวันที่เกิดการหยุดปฏิบัติงานลงตาราง `holidays`
   - **การแปลงปีปฏิทิน (Buddhist Era Normalization):** ระบบรองรับการเขียนข้อมูลวันหยุดปีพุทธศักราช (พ.ศ. > 2400) โดยระบบจะปรับลดค่าลง 543 ปีเป็นคริสต์ศักราช (ค.ศ.) โดยอัตโนมัติเพื่อให้เก็บเป็นรูปแบบมาตรฐาน `YYYY-MM-DD`
2. **ผลลัพธ์และการทำงาน:**
   - คิวรีข้อมูลวันทำงานและแสดงผลในรูปแบบ Calendar Grid (Month/Year Views)
   - หักลบเวลาของวันเหล่านั้นไม่ให้ถูกนับในระบบวัดผลความรวดเร็วการให้บริการ (SLA)
   - รองรับการ Import CSV วันหยุดจำนวนมาก และมีระบบบันทึก Audit Logs ทุกขั้นตอน

### 7.4 นโยบายข้อตกลงและเงื่อนไข (SLA Settings)
1. **ขีดจำกัด SLA (SLA Targets):**
   - กำหนดเกณฑ์เป้าหมายการให้บริการแยกตามระดับความรุนแรง (Severity: High/Medium/Low) สำหรับ Response และ Resolution
   - รูปแบบการบันทึกจะใช้เกณฑ์วันทำงานบวกกับเวลานาทีทำการจริง (`DAY + HH:mm` เช่น `3 + 00:00` หรือ `0 + 06:30`) ระบบจะนำมาคูณหาค่านาทีรวม (`Business Minutes`) อัตโนมัติและบันทึกลงฐานข้อมูล `system_settings` คีย์ `sla_limits`
2. **การระงับนับเวลาชั่วคราว (SLA Exclusion Reason):**
   - เก็บรหัสเหตุผลที่สามารถระงับเวลาได้ชั่วคราว เช่น ระหว่างรอข้อมูลเพิ่มเติมจากผู้ใช้ หรือรอคิวอุปกรณ์จาก Vendor ภายนอก
   - บันทึกและดึงข้อมูลจากตาราง `master_data` คีย์ `type = 'sla_exclusion_reason'` รองรับการกดเปลี่ยนสถานะเปิด/ปิดการใช้งาน (Active/Inactive)

## 🗃️ 8. ขั้นตอนการทำงานของฟังก์ชัน Master Data (Master Data Flow)

ระบบจัดการข้อมูลหลัก (Master Data) ของ Dowa IT System ถูกออกแบบโดยการใช้สถาปัตยกรรมแบ่งกลุ่ม (Forced Group) ผ่านหน้าจอ Component ร่วมตัวเดียว (`MasterDataScope.js`) ควบคุมสิทธิ์การจัดเก็บข้อมูลผ่านพฤติกรรมและการกระทำดังนี้:

### 8.1 การคัดแยกและเส้นทางเข้าถึง (Routing & Navigation Groups)
* **Incident Setup:** แสดงเฉพาะรายการที่ผูกกับใบแจ้งซ่อม ได้แก่:
  1. `Incident Category` (หมวดหมู่ประเภทปัญหา คีย์: `incident_category`)
  2. `Affected System` (ระบบหรืออุปกรณ์ที่ได้รับผลกระทบ คีย์: `affected_system`)
  3. `SLA Exclusion Reason` (เหตุผลการหยุดเวลาทำการ คีย์: `sla_exclusion_reason`)
* **Checklist Setup:** แสดงรายการตั้งต้นสำหรับใบตรวจเช็ค ได้แก่:
  1. `Checklist Category` (หมวดหมู่การตรวจเช็ค คีย์: `checklist_category`)
  2. `Checklist Master` (รายการหัวข้อตรวจเช็ค คีย์: `checklist_template`)
  3. `Target Registry` (ทะเบียนเป้าหมายตรวจเช็คและค่าพิกัด คีย์: `target_registry`)
  4. `Procedure Plans` (แผนลำดับขั้นตอน SOP คีย์: `procedure_plan`)

### 8.2 ลำดับและพฤติกรรมของระบบข้อมูล (Execution Sub-Flows)

#### 1) การจัดการข้อมูลมาตรฐาน (Standard Master Data Flow)
*   **Trigger:** ผู้ใช้เพิ่ม ลบ หรือสลับสถานะของข้อมูลหมวดหมู่ทั่วไป (Category, System, SLA Reasons)
*   **Inputs:** `newValue` (ค่าข้อความที่กรอกใหม่) หรือการเลือกสลับปุ่มสถานะ
*   **Decision Matrix:**
    *   **Add (การเพิ่ม):** ตรวจสอบไม่ให้กรอกค่าว่าง คำนวณอันดับลำดับการจัดเรียง (`sort_order = maxOrder + 1`) และบันทึกลงฐานข้อมูลโดยตั้งต้นสถานะเป็นเปิดใช้งาน (`is_active = true`)
    *   **Inline Edit (แก้ไขทันที):** เมื่อผู้ใช้คลิกช่องรายการและทำการเบลอเมาส์ออก (`onBlur`) ระบบจะส่งข้อมูลอัปเดตฟิลด์ข้อความลงฐานข้อมูลโดยตรง
    *   **Toggle (สลับสถานะ):** เปลี่ยนสถานะการมองเห็นโดยอ้างอิงบูลีน `!currentStatus` ของรายการนั้น เพื่อช่วยซ่อนข้อมูลไม่ให้แสดงผลหน้าบ้านแทนการลบแถวประวัติเก่าในฐานข้อมูล
*   **Outputs & DB Effects:** บันทึกข้อมูลลงตาราง `master_data` พร้อมสร้างประวัติ Audit Log เปรียบเทียบข้อมูลก่อนการแก้ไข (`before`) และหลังแก้ไข (`after`)

#### 2) การจัดการ Checklist Template และ SOP (Template & SOP Flow)
*   **Trigger:** ผู้ใช้สร้าง ปรับเปลี่ยน หรือจำลองแบบฟอร์มตรวจสอบของ Checklist
*   **Inputs & States:** `freqFilter` (ฟิลเตอร์แยกประเภทความถี่), ข้อมูล UI Template (T0 - T5)
*   **Decision Matrix:**
    *   **Preview Mode:** เมื่อผู้ใช้กดปุ่มรูปดวงตา (`👁 Preview`) ระบบจะดึงแผน SOP ที่ผูกไว้จากตาราง `checklist_procedure_plans` และแสดงแบบฟอร์มจำลองเสมือนจริงในหน้าต่าง Modal
    *   **Template / Plan Builder:** ปุ่มแก้ไขจะทำการเปลี่ยนเส้นทางไปยังหน้า `checklist-template-builder` หรือ `procedure-plan-editor` เพื่อจัดการความเรียบร้อย
*   **Outputs & DB Effects:** อัปเดตโครงสร้างฟอร์มในตาราง `checklist_templates` หรือ `checklist_procedure_plans` และบันทึก Audit Logs ทุกรายการเปลี่ยนแปลง

## 🔄 9. ขั้นตอนการทำงานของฟังก์ชัน Workflow & Approval (Workflow & Approval Flow)

ระบบควบคุมลำดับการอนุมัติ (Workflow Rules) และระบบผู้ทำการแทนชั่วคราว (Substitute Approvers) เพื่อรักษาความต่อเนื่องของกระบวนการอนุมัติในองค์กร มีกระบวนการดำเนินงานดังนี้:

### 9.1 บทบาทผู้อนุมัติสองรูปแบบ (Approval Role Model)
1. **System Roles (บทบาทระบบ):** 
   - สิทธิ์ถูกผูกตายตัวกับระดับบัญชีผู้ใช้งาน ได้แก่ `admin` (ผู้ดูแลระบบ), `it_staff` (เจ้าหน้าที่ไอที), `approver` (ผู้อนุมัติ/หัวหน้างาน), `employee` (พนักงานทั่วไป) และ `auditor` (ผู้ตรวจสอบ)
2. **Dynamic Roles (บทบาทแปรผันตามประเภทเอกสาร):**
   - **Creator (ผู้สร้างเอกสาร):** คำนวณจากคีย์ `created_by_id` หากไม่พบจะใช้ `reported_by_id` แทน
   - **Reporter (ผู้แจ้งเรื่อง):** คำนวณจากคีย์ `reported_by_id` หากไม่พบจะใช้ `created_by_id` แทน
   - *หมายเหตุ:* การใช้บทบาทแปรผันช่วยป้องกันความสับสนกรณีเจ้าหน้าที่ไอทีเป็นผู้กรอกข้อมูลแจ้งซ่อมแทนพนักงาน

### 9.2 ลำดับขั้นตอนการทำงาน (Sub-Flows & Logic Steps)

#### 1) การตั้งค่าลำดับขั้นตอนอนุมัติ (Workflow Setup Flow)
*   **Trigger:** ผู้ดูแลระบบตั้งขั้นตอนการอนุมัติสำหรับ Checklist (ตามความถี่) หรือ Incident (ตามความรุนแรง)
*   **Inputs:** ลำดับขั้นตอนอนุมัติ (`step_order`), บทบาทที่ต้องการ (`role_required`), ผู้อนุมัติเฉพาะเจาะจง (`approver_id`)
*   **Conditional Branches & Guardrails:**
    *   **บทบาทเฉพาะเจาะจง:** หากมีการเลือก `approver_id` ระบบจะกรอกสิทธิ์บทบาท `role_required` ให้ตรงกับบทบาทของบุคคลนั้นโดยอัตโนมัติ
    *   **Incident Workflow Guardrail:** ระบบกำหนดกฎห้ามผู้ดูแลระบบบันทึกโครงสร้างขั้นตอน Incident หากไม่มีการผูกขั้นตอนให้บทบาทแปรผัน (`reporter` หรือ `creator`) อย่างน้อย 1 ขั้นตอน เพื่อป้องกันไม่ให้เคสปิดโดยไม่มีการยืนยันการปฏิบัติงานสำเร็จจากผู้แจ้ง
*   **Outputs & DB Effects:** บันทึกโครงสร้างใหม่ลงตาราง `workflow_configs` (โดยลบข้อมูลแถวเดิมของ config นั้นและแทรกชุดใหม่แบบเรียงอันดับ)

#### 2) นโยบายการผ่านอนุมัติอัตโนมัติ (Auto-Approval Rule Policy)
*   **Trigger:** ผู้ใช้ทำการกดส่งอนุมัติเอกสารหลักเข้าระบบ
*   **Decision Matrix:**
    *   *ระบบตรวจพบคอนฟิกมีขั้นตอน (Steps > 0):* สร้างรายการขั้นตอนอนุมัติลงตาราง `document_approvals` เพื่อรอการเซ็นชื่อและยืนยันตัวตนด้วย PIN/OTP
    *   *ระบบตรวจพบว่าไม่มีขั้นตอนอนุมัติในตาราง (Steps = 0):* เรียกใช้ระบบ **Auto-Approval** ทำเครื่องหมายให้เอกสารผ่านการอนุมัติระดับสูงทันที
*   **Outputs & DB Effects:** สถานะของเอกสารจะถูกเปลี่ยนเป็น **Closed** และ **approved** ทันที พร้อมเขียน Audit Log ระบุเหตุผลการอนุมัติอัตโนมัติ (Auto-Approved) และยิง Post-Approval Sync ไปยังโมดูลที่เกี่ยวข้อง

#### 3) การจัดการผู้ทำงานแทนชั่วคราว (Absence & Substitution Flow)
*   **Trigger:** ผู้อนุมัติทำการแจ้งวันหยุดไม่อยู่ปฏิบัติงานพร้อมระบุคนลงนามแทน
*   **Inputs:** วันที่ไม่อยู่ปฏิบัติงาน (`start_date` - `end_date`), คนทำงานแทน (`substitute_id`), และเหตุผล
*   **Conditional Branches & Rules:**
    *   **แนะนำคนแทน:** ระบบกรองเฉพาะรายชื่อผู้ใช้ที่อยู่ในสิทธิ์ Role กลุ่มเดียวกันเพื่อแนะนำผู้อนุมัติแทน
    *   **การอนุมัติแทน:** เมื่อมีเอกสารวิ่งเข้ามาหาผู้อนุมัติหลักในช่วงหน้าต่างวันไม่อยู่ ระบบจะส่ง Notification หาทั้งตัวจริงและคนแทน
    *   คนแทนสามารถเซ็นชื่อโดยกรอกรหัส **Signature PIN 6 หลักของตนเอง** ลงบนอุปกรณ์ และระบบจะลงบันทึกในเอกสารและ Audit Log ว่า "อนุมัติโดย: คนแทน (แทนผู้รับผิดชอบหลัก...)"
*   **Outputs & DB Effects:** เพิ่มและบันทึกช่วงสิทธิ์การแทนลงตาราง `approval_substitutes` พร้อมบันทึกประวัติการเปลี่ยนแปลงสิทธิ์

### 🔄 101. ขั้นตอนการทำงานของ Incident (ใบแจ้งซ่อม)

กระบวนการของ Incident มีความพิเศษคือมีการ "รวบรวมลายเซ็น" ในขั้นตอนการ Resolve เพื่อลดความซ้ำซ้อน

#### 📌 Flow แผนผังการทำงาน:
1.  **สร้างเคส (Open)**: User แจ้งปัญหา สถานะเริ่มต้นคือ `Open`
2.  **มอบหมายงาน (In Progress)**: เมื่อมีการ Assign ผู้รับผิดชอบ สถานะจะเปลี่ยนเป็น `In Progress` โดยอัตโนมัติ
3.  **การแก้ไขและ Resolve (Resolve Dialog)**:
    *   IT Officer กด Resolve
    *   **ขั้นตอนการเซ็น**:
        1. IT เซ็นชื่อของตนเอง
        2. ผู้แจ้ง (Reporter) ยืนยันตัวตนด้วย PIN และเซ็นชื่อ
        3. (ถ้า Severity = High) ผู้จัดการต้องเซ็นชื่อ
    *   **Logic การบันทึก**: เมื่อกด Submit ระบบจะเรียก `submitRequest()` และ `applySignaturesToWorkflow()` เพื่อนำลายเซ็นที่ได้ไปเติมลงใน Workflow Steps ทันที (Auto-consume)
4.  **ตรวจสอบสถานะ (Status Check)**:
    *   ถ้าเซ็นครบทุกขั้นตอนตาม Config -> สถานะเป็น `Closed` ทันที
    *   ถ้ายังไม่ครบ (เช่น ขาดลายเซ็นผู้จัดการ) -> สถานะเป็น `Pending Approval`
5.  **การปิดเคส (Closed)**: เมื่อขั้นตอนสุดท้ายได้รับการอนุมัติ ระบบจะรัน `onDocumentFinalApproval` เพื่อซิงค์ข้อมูลกลับไปยัง Checklist (ถ้ามี)

#### Audit Expectations ระหว่างแก้เอกสาร
- การแก้ Incident detail ต้องสร้าง canonical `Updated` structured audit entry พร้อม `field_changes`
- การแก้ Checklist detail ต้องสร้าง structured audit entry ทั้งระดับเอกสารและระดับ item ตามจุด mutation สำคัญ

#### ⚖️ เงื่อนไข Yes/No ใน Incident Resolve:
*   **เป็นงานที่มาจาก Checklist?**
    *   `Yes` -> เมื่อเคสถูกปิด ระบบจะไป Update รายการ Checklist นั้นเป็น `OK` อัตโนมัติ
    *   `No` -> ปิดเคสตามปกติ
*   **ระดับความรุนแรง (Severity) คืออะไร?**
    *   `High` -> ระบบจะเพิ่มขั้นตอนการอนุมัติลำดับที่ 3 (Manager) ให้อัตโนมัติ
    *   `Low/Medium` -> มีเพียง 2 ขั้นตอน (IT & Reporter)

### 📋 102. ขั้นตอนการทำงานของ Checklist (การตรวจเช็คประจำวัน)

#### 📌 Flow แผนผังการทำงาน:
1.  **เริ่มการตรวจ (Open)**: เจ้าหน้าที่เริ่มกรอกข้อมูลตาม Template (T1-T5)
2.  **ส่งขออนุมัติ (Submit)**: เมื่อกรอกครบและบันทึก ระบบจะเรียก `submitRequest()`
3.  **สร้างขั้นตอนอนุมัติ**: ระบบดึงข้อมูลจาก `workflow_configs` มาสร้าง Steps ใน `document_approvals`
4.  **ผู้อนุมัติพิจารณา (Approval UI)**:
    *   ผู้อนุมัติเห็นรายการในเมนู "งานรอกดอนุมัติ"
    *   **ทางเลือก (Action)**:
        *   ✅ **อนุมัติ (Approve)**: เซ็นชื่อ -> ปลดล็อคขั้นตอนถัดไป (Waiting -> Pending)
        *   ❌ **ตีกลับ (Reject)**: ใส่เหตุผล -> เอกสารกลับไปสถานะ `Open` (ร่าง) เพื่อให้แก้ไขใหม่
5.  **เสร็จสิ้น (Closed)**: เมื่อคนสุดท้ายเซ็นครบ สถานะจะเป็น `Closed`

#### Audit Expectations ระหว่างลงผลตรวจ
- การเปลี่ยน `evaluation_result`, `evaluation_remark`, `status`, `duration`, `start_time` และ `template_data` ต้องถูกบันทึกเป็น structured audit event
- `template_data` ต้อง log แบบ summary เท่านั้น ห้าม dump payload ดิบทั้งก้อน

### 🔒 103. การยืนยันตัวตน (Authentication Modes)

|---|---|---|
| มีอีเมลในระบบอยู่แล้ว และ Onboard สำเร็จ | แจ้งข้อผิดพลาด (Email Onboarded) | ไม่มีผลใดๆ ในระบบ |

| กำหนดบทบาทเป็น `it_staff` | ระบบตั้งค่าให้สามารถรับมอบหมายงาน Incident ได้ | `user_profiles.can_be_assignee = true` |

#### B. การต่ออายุ Auditor (Auditor Expiry Flow)
| เงื่อนไข / สถานะปัจจุบัน (Current State) | การเลือกวันต่ออายุ (+3, +7, +15, +30 วัน) | ผลลัพธ์และผลกระทบ (DB Side Effects) |
|---|---|---|
| บัญชียังไม่หมดอายุ (`expires_at` > ปัจจุบัน) | บวกวันต่อจากค่า `expires_at` เดิม | อัปเดต `expires_at` ใหม่, บันทึก `admin_audit_logs` |
| บัญชีหมดอายุแล้ว (`expires_at` <= ปัจจุบัน) | บวกวันต่อจากเวลาปัจจุบัน (`NOW`) | อัปเดต `expires_at` ใหม่, ตั้งค่าบัญชีเป็น `is_active = true`, บันทึก `admin_audit_logs` |

#### C. การปลดล็อคและกู้คืน PIN (Signature PIN Recovery Flow)

### 10.3 ขั้นตอนการทำงานสำหรับนำไปวาด Flowchart (Flowchart Blueprint)

#### Flow 1: การสร้างบัญชีผู้ใช้ใหม่ (Create User Flow)
1.  **Trigger**: ผู้ดูแลระบบกดปุ่ม `+ Create User` และกรอกข้อมูลฟอร์มส่งบันทึก (`onSubmit`)
2.  **Inputs**:
    *   `email` (string)
    *   `full_name` (string)
    *   `role` (string: admin / it_staff / approver / employee / auditor)
    *   `password` (string - ตัวเลือก)
    *   `sendEmailInvite` (boolean)
3.  **Conditional Branches**:
    *   **ตรวจสอบอีเมลซ้ำ**:
        *   พบใน `user_profiles` และ Onboard แล้ว -> ❌ แจ้งข้อผิดพลาด (Email Onboarded) -> จบขั้นตอน
        *   พบใน `user_profiles` แต่ยังไม่ Onboard -> ❌ แจ้งข้อผิดพลาดให้ลบของเก่า -> จบขั้นตอน
        *   พบเฉพาะใน `auth.users` (ไม่มี Profile) -> 🛡️ **Self-Healing**: ลบผู้ใช้เก่าใน Auth -> ประมวลผลต่อ
        *   ไม่พบข้อมูลเดิม -> ประมวลผลต่อ
    *   **คัดกรองสิทธิ์และพารามิเตอร์**:
        *   ถ้า `role` == `'auditor'` -> คำนวณวันหมดอายุเริ่มต้น `expires_at = NOW + 3 Days`
        *   ถ้า `role` == `'it_staff'` -> กำหนดสิทธิ์ผู้รับงาน `can_be_assignee = true`
        *   ถ้าไม่ใช่ -> `expires_at = null` และ `can_be_assignee = false`
    *   **วิธีการลงทะเบียน (Password vs Invite)**:
        *   หากระบุ `password` -> ใช้รหัสผ่านนั้นในการเปิดสิทธิ์ + แจ้งยืนยันความประสงค์การส่ง Email
        *   หากปล่อย `password` ว่าง -> ทำระบบสุ่มรหัสผ่าน + ตั้งเป้าหมายให้ทำ Self-Registration
4.  **Outputs & Database Side Effects**:
    *   แทรกข้อมูลผู้ใช้ใหม่ลงใน Supabase Auth (`auth.users`)
    *   บันทึก SHA-256 Hash ของอีเมลลงตาราง `user_whitelist`
    *   บันทึกโปรไฟล์ลงตาราง `user_profiles` พร้อมระบุ `onboarding_token`
    *   ทำการลิงก์งาน Incident ย้อนหลังจากอีเมลเข้าระบบ Profile อัตโนมัติ (`autoLinkIncidentsByReporterEmail`)
    *   บันทึกประวัติการสร้างลงตาราง `admin_audit_logs`
    *   (ถ้าเลือกส่งเมล์) ส่งอีเมลเชิญหรือแจ้งข้อมูลรหัสผ่านผ่านบริการ Resend

#### Flow 2: การจัดการสิทธิ์การเข้าถึง (Permission Management Flow)
1.  **Trigger**: ผู้ดูแลระบบเข้าไปที่หน้าจอ `Permissions` เปลี่ยนสิทธิ์ในตารางแบบ Dynamic และกดบันทึก (`Save Changes`)
2.  **Inputs**: รายการอัปเดตสิทธิ์ในรูปแบบอาร์เรย์ `[{ role_name, feature_key, access_level }]`
    *   `access_level` มี 3 ระดับ: `RW` (Read & Write), `RO` (Read Only), `NONE` (No Access)
3.  **Conditional Branches**:
    *   ตรวจสอบว่ามีค่าใดเปลี่ยนแปลงจากตารางเดิมหรือไม่ (`hasChanges`)
        *   ไม่มี -> ปุ่ม Save ปิดการใช้งาน -> จบขั้นตอน
        *   มี -> อนุญาตให้ส่งคำร้องบันทึกข้อมูล
4.  **Outputs & Database Side Effects**:
    *   ทำการปรับปรุงหรือบันทึกใหม่ลงตาราง `permission_sets` (ใช้คำสั่ง `upsert` บน Key: `role_name, feature_key`)

    *   หน้า Sidebar เมนูและสิทธิ์ในแต่ละโมดูลจะปรับเปลี่ยนตามการตั้งค่าใหม่โดยทันที

        *   ไม่ผ่าน $\rightarrow$ ปุ่มส่งถูกล็อก / แสดงแจ้งเตือน $\rightarrow$ จบการทำงาน

### 13.2 โครงสร้างการตัดสินใจและทางเลือก (Decision Matrix)

#### A. การประเมินสถานะเซสชันของบุคคล (User Session Checking Matrix)
| สถานะคุกกี้ / การร้องขอเซสชัน | การตรวจสอบใน Database (Security & State Check) | ผลลัพธ์และสิทธิ์เข้าใช้ (Session Result) |
|---|---|---|
| พบ Cookie `guest-session` และยังไม่หมดอายุ | - | ✅ สิทธิ์การใช้งานระดับ `external` (บุคคลภายนอก) |
| ตรวจพบ Supabase User Session | `user_profiles.is_active === false` (ถูกระงับสิทธิ์) | ❌ บัญชีถูกระงับ $\rightarrow$ ระบบเรียก `signOut()` และดีดไปหน้าแรกพร้อม Error |
| ตรวจพบ Supabase User Session | `user_profiles.is_onboarded === false` (ยังไม่เสร็จสิ้น) | ❌ ยังไม่ได้ Onboard $\rightarrow$ ระบบดีดไปหน้า `/onboarding?token=...` เพื่อตั้งรหัสผ่าน/PIN ครั้งแรก |
| ตรวจพบ Supabase User Session (Auditor) | `expires_at < NOW` (หมดเวลาบัญชีชั่วคราว) | ❌ บัญชีหมดอายุ $\rightarrow$ ปรับปรุงคอลัมน์ `is_active = false`, เรียก `signOut()` และยกเลิกเซสชันทันที |
| ตรวจพบ Supabase User Session และตรงตามเงื่อนไข | ผ่านการตรวจสอบ Whitelist, Active และ Onboard แล้ว | ✅ สิทธิ์การใช้งานระดับ `internal` (พนักงาน/Admin) |

#### B. สิทธิ์การเปิด/ปิดเมนูและฟังก์ชัน (Page Permission Routing Matrix)
| สิทธิ์/ระดับสิทธิ์ในฟีเจอร์ (checkPermission) | การดำเนินการบนหน้าจอ (Access Policy) | ผลลัพธ์ UI (UI Control) |
|---|---|---|
| `NONE` | ดีดออกจากหน้าจอนั้นทันที $\rightarrow$ ส่งไปที่ `/dashboard?error=access_denied` | ลบเมนูออกจากแถบ Sidebar |
| `RO` (Read Only) | บังคับปิดฟังก์ชันแก้ไข (Grayscale/Disabled) ทั้งหมดใน Main Content | แสดงแบนเนอร์แจ้งเตือนสีแดงด้านบน และล็อกการส่งฟอร์ม/กดปุ่ม |
| `RW` (Read & Write) | อนุญาตให้ทำงานได้อย่างอิสระตามความเหมาะสมของฟีเจอร์ | ปุ่มบันทึกข้อมูลและฟอร์มเปิดใช้งานตามปกติ |

### 13.3 ขั้นตามการทำงานสำหรับนำไปวาด Flowchart (Flowchart Blueprint)

#### Flow 1: การตรวจสอบเซสชันและการเข้าหน้าจอ (Session Checking Flow)
1.  **Trigger**: มีการเปลี่ยนเส้นทาง URL หรือผู้ใช้รีเฟรชหน้าจอในส่วน `/dashboard`
2.  **Inputs**: คุกกี้เซสชัน (`guest-session`, Supabase Token) และ URL Path ปัจจุบัน
3.  **Conditional Branches**:
    *   **ตรวจสอบ Cookie `guest-session`**:
        *   พบและยังไม่หมดอายุ $\rightarrow$ ✅ คืนค่าเซสชันแบบ `external`
    *   **ตรวจสอบ Supabase Session**:
        *   ไม่พบเซสชันใดๆ $\rightarrow$ ❌ ดีดส่งกลับไปหน้าแรก (`/`) $\rightarrow$ จบขั้นตอน
        *   พบเซสชัน $\rightarrow$ ดึงรายละเอียดโปรไฟล์จากตาราง `user_profiles`
    *   **ตรวจสอบความพร้อมใช้งานของบัญชี (Security Validation)**:
        *   ถ้า `is_active === false` $\rightarrow$ ❌ สั่ง `signOut()` และเด้งกลับหน้าแรกพร้อม Error
        *   ถ้า `is_onboarded === false` $\rightarrow$ ❌ เด้งผู้ใช้ไปยังหน้า `/onboarding` เพื่อทำรายการตั้งค่าครั้งแรก
        *   (เฉพาะผู้ใช้ Auditor) หากวันหมดอายุ `expires_at < NOW` $\rightarrow$ ❌ ปรับ `is_active = false` บน Profile $\rightarrow$ สั่ง `signOut()` $\rightarrow$ ดีดส่งกลับหน้าแรก
    *   **ตรวจสอบสิทธิ์เข้าถึงหน้าจอ (Permission Check)**:
        *   ดึงชุดข้อมูลสิทธิ์ Dynamic ผ่านฟังก์ชัน `getRolePermissions`
        *   เรียกตรวจสอบสิทธิ์กับฟีเจอร์เป้าหมาย (`checkPermission`)
        *   ถ้าได้ระดับ `NONE` (และไม่ใช่หน้าส่วนตัว) $\rightarrow$ ❌ เด้งกลับหน้าหลัก `/dashboard?error=access_denied`
        *   ถ้าได้ระดับ `RO` $\rightarrow$ ล็อคอินพุตและปุ่มทั้งหมดบน UI (Gray-out)
        *   ถ้าได้ระดับ `RW` $\rightarrow$ เปิดสิทธิ์ทำงานครบถ้วน

#### Flow 2: กระบวนการออกจากระบบ (Logout Flow)
1.  **Trigger**: ผู้ใช้คลิกปุ่ม `ออกจากระบบ` ที่แถบล่างสุดของ Sidebar
2.  **Inputs**: เซสชันปัจจุบันของผู้ใช้งานที่ Login อยู่
3.  **Outputs & Database Side Effects**:
    *   ดึงรายละเอียด ID และอีเมลของผู้ใช้ล่าสุด
    *   `INSERT` ประวัติการทำรายการลงตาราง `login_logs` โดยระบุ `action = 'logout'` และรายละเอียด User Agent ของอุปกรณ์
    *   เรียกใช้ API `supabase.auth.signOut()` เพื่อล้าง Token ล็อกอินทั้งหมด
    *   ทำการเด้งผู้ใช้งานกลับไปสู่หน้าลงชื่อเข้าใช้หน้าแรก (`/`) ทันที
