คำอธิบายภาษาไทย — ฉบับอ่านเข้าใจง่าย
วันที่จัดทำ: 29 เมษายน 2569

=======================================================
ส่วนที่ 1: ระบบนี้คืออะไร และทำไมต้องทำ
=======================================================

ระบบ RBAC (Role-Based Access Control) คือการกำหนดสิทธิ์การเข้าถึงระบบตาม "บทบาท" ของผู้ใช้งาน
แทนที่จะให้ทุกคนเข้าถึงได้เท่ากัน เราจะแบ่งว่าใครทำอะไรได้บ้างในระบบ

ปัญหาที่แก้:
- ระบบปัจจุบันมีแค่ 2 บทบาท คือ superuser (Admin) กับ visitor (อ่านอย่างเดียว)
- ยังขาดบทบาทที่จำเป็น เช่น Supervisor ที่ทำงานได้แต่ไม่แตะ Settings
  และ Approval ที่มีหน้าที่เซ็นต์อนุมัติเอกสารเท่านั้น
- ยังไม่มีการป้องกัน Route ที่ Server ทำให้มีช่องโหว่ด้านความปลอดภัย

=======================================================
ส่วนที่ 2: ผู้ใช้งาน 4 ประเภท
=======================================================

บทบาทที่ 1 — Administrator (ผู้ดูแลระบบสูงสุด)
  ทำได้ทุกอย่างในระบบโดยไม่มีข้อจำกัด ทั้งสร้าง แก้ไข ลบ ตั้งค่า
  และจัดการ User คนอื่นๆ ได้ทั้งหมด
  Login ด้วย Email + Password ผ่าน Supabase เหมือนเดิม

บทบาทที่ 2 — Supervisor (หัวหน้างาน)
  ทำงานประจำวันได้ทุกอย่าง เช่น บันทึก Incident, ดู Backup Log, 
  ใช้งาน Dashboard แต่ไม่สามารถเข้าเมนู Settings ได้เลย
  ไม่ว่าจะเป็น Master Data, No. Series หรือจัดการ User
  Login ด้วย Email + Password เหมือน Administrator

บทบาทที่ 3 — Approval (ผู้อนุมัติเอกสาร)
  มีหน้าที่เดียวคือรับ Link ทาง Email แล้วคลิกเข้ามาดูเอกสารที่ต้องอนุมัติ
  สามารถกด Approve หรือ Reject พร้อมใส่ comment ได้
  ไม่ต้องมี account ในระบบ ไม่ต้อง Login ด้วย Password
  แค่คลิก Link จาก Email ก็เข้าถึงเอกสารนั้นๆ ได้เลย
  รองรับหลายประเภทเอกสาร เช่น Incident Report, Backup Report, IT Checklist

บทบาทที่ 4 — Guest (ผู้เยี่ยมชมระบบ)
  ดูข้อมูลได้อย่างเดียว แก้ไขอะไรไม่ได้เลย เหมาะสำหรับ Auditor 
  หรือผู้ที่ต้องการดูภาพรวมระบบ จะมองไม่เห็นเมนูที่เกี่ยวกับความปลอดภัย
  Admin กำหนดได้ว่า Guest คนนี้จะดูได้กี่วัน เมื่อหมดอายุระบบจะปิดอัตโนมัติ

=======================================================
ส่วนที่ 3: ระบบ Identity แบบ 2 ชั้น
=======================================================

เราแบ่งการจัดการ Identity ออกเป็น 2 ระดับ เพราะ Administrator กับ Supervisor
ต้องการความปลอดภัยสูงกว่า มี Password จริง มี Session และมีการ Login แบบปกติ
ในขณะที่ Approval กับ Guest ไม่จำเป็นต้องมี account เต็มรูปแบบ

ชั้นที่ 1 (Administrator, Supervisor):
  เก็บใน Supabase Auth ซึ่งเป็นระบบ Authentication มาตรฐาน
  มี JWT Token, มี Session, Login ด้วย Email + Password
  หากไม่ได้ใช้งาน Session จะหมดอายุตามปกติ

ชั้นที่ 2 (Approval, Guest):
  เก็บในตาราง external_users ที่เราสร้างเอง
  ไม่มี Supabase Account ไม่มี Password ในระบบ
  ใช้ Token แบบสุ่ม 64 ตัวอักษรแทน เก็บในฐานข้อมูล
  Approval ได้รับ Token ผ่าน Email Link (ใช้ครั้งเดียวแล้วหมดอายุ)
  Guest ได้รับ Token ที่ใช้ได้ตามระยะเวลาที่ Admin กำหนด

ตารางกลาง (user_registry):
  เป็นตารางที่เชื่อม 2 ชั้นเข้าด้วยกัน เก็บประวัติทุกคนไว้ในที่เดียว
  ทำให้เมื่อมีการเปลี่ยน Role ข้ามชั้น ยังคง Audit Trail ไว้ได้ครบถ้วน

=======================================================
ส่วนที่ 4: ใครเข้าอะไรได้บ้าง
=======================================================

หน้า Dashboard หลัก:
  - Administrator, Supervisor, Guest เข้าได้ทั้งหมด
  - Approval เข้าไม่ได้ มีแค่หน้าเอกสารที่ส่ง Link มาให้เท่านั้น

หน้า Incident, Backup, Checklist:
  - Administrator กับ Supervisor เข้าได้และแก้ไขได้
  - Guest เข้าได้แต่ดูอย่างเดียว ปุ่มสร้าง/แก้ไขจะซ่อนอยู่
  - Approval เข้าไม่ได้

หน้า Settings ทุกหน้า (Users, Master Data, No. Series, Working Hours):
  - Administrator เท่านั้น
  - Supervisor, Approval, Guest เข้าไม่ได้เด็ดขาด

หน้า Profile (ข้อมูลส่วนตัว):
  - Administrator กับ Supervisor เข้าได้
  - Approval กับ Guest เข้าไม่ได้

=======================================================
ส่วนที่ 5: เครื่องมือที่ใช้ (ฟรีทั้งหมด)
=======================================================

Supabase Auth:
  ใช้จัดการ Identity ของ Administrator และ Supervisor
  มีอยู่แล้วในโปรเจกต์ ไม่ต้องติดตั้งเพิ่ม

Resend.com:
  บริการส่ง Email สำหรับ Transactional Email เช่น Approval Link, Guest Invite
  และ PIN Reset Email ฟรี 3,000 ฉบับต่อเดือน
  ซึ่งระบบนี้ใช้แค่ประมาณ 20 ฉบับต่อเดือน ถือว่าน้อยมาก
  Email ประเภทนี้ไม่ใช่ Spam เพราะส่งเฉพาะคนที่ทำ action ในระบบ
  มีระบบ SPF/DKIM/DMARC ที่ทำให้ Email ไปถึง Inbox ได้อย่างน่าเชื่อถือ

bcryptjs:
  Library สำหรับ Hash PIN Code ก่อนบันทึกลงฐานข้อมูล
  ทำให้แม้ฐานข้อมูลโดน breach ก็ไม่มีใครรู้ PIN จริงๆ ของผู้ใช้งาน

Next.js Middleware:
  ระบบป้องกัน Route ที่ทำงานที่ Server ก่อนที่ Browser จะเห็นหน้าใดๆ
  ปลอดภัยกว่าการป้องกันฝั่ง Client อย่างที่ทำอยู่ในปัจจุบัน

=======================================================
ส่วนที่ 6: ฟีเจอร์ PIN Code
=======================================================

PIN เป็นรหัสผ่านสั้น 4-6 หลัก ที่ผู้ใช้สามารถตั้งไว้ได้ (ไม่บังคับ)
เพื่อใช้แทนการ Login ด้วย Password หรือใช้ยืนยันตัวตนเมื่อคลิก Link จาก Email

การทำงาน:
  เมื่อ Admin สร้าง User ใหม่ ระบบจะแสดงช่องให้ตั้ง PIN แบบ Optional
  พร้อมคำแนะนำว่า "PIN ช่วยให้ยืนยันตัวตนได้เร็วขึ้น ไม่ต้องกรอก Password ทุกครั้ง"
  ถ้าไม่ตั้งก็ข้ามได้เลย ระบบจะไม่บังคับ

สำหรับ Approval/Guest เมื่อคลิก Link มาจาก Email:
  ถ้ามี PIN → ระบบจะให้กรอก PIN ก่อนจึงจะเข้าดูเนื้อหาได้
  ถ้าไม่มี PIN → เข้าดูได้เลยทันที

การ Reset PIN:
  ทำได้โดย Admin เท่านั้น โดยกดปุ่ม "Send PIN Reset" ในหน้าจัดการ User
  ระบบจะส่ง Email พร้อม Link ให้ผู้ใช้ตั้ง PIN ใหม่ด้วยตัวเอง
  Link จะหมดอายุภายใน 1 ชั่วโมงเพื่อความปลอดภัย
  Admin จะไม่รู้ PIN ของผู้ใช้ เพราะเก็บเป็น Hash เท่านั้น

=======================================================
ส่วนที่ 7: การจัดการ Guest Access
=======================================================

เมื่อ Admin สร้าง Guest ใหม่:
  ต้องระบุจำนวนวันที่จะให้ Guest คนนั้นเข้าระบบได้ เช่น 7 วัน หรือ 30 วัน
  ระบบจะคำนวณวันหมดอายุเอง แล้วส่ง Email พร้อม Link ให้ Guest

สถานะของ Guest ในหน้า Users:
  สีเขียว (Active) — ยังใช้ได้ปกติ
  สีเหลือง (Expiring) — จะหมดอายุในอีกไม่ถึง 2 วัน ควรต่ออายุ
  สีแดง (Expired) — หมดอายุแล้ว เข้าระบบไม่ได้
  สีเทา (Disabled) — Admin ปิดการใช้งานไว้ชั่วคราว

Admin สามารถ:
  Disable Guest ได้ทันทีโดยไม่ต้องรอหมดอายุ
  Enable Guest กลับมา พร้อมระบุระยะเวลาใหม่ได้เสมอ

=======================================================
ส่วนที่ 8: การเปลี่ยน Role ข้ามระดับ
=======================================================

กรณีที่ 1 — เปลี่ยน Administrator/Supervisor ไปเป็น Approval/Guest:
  ระบบจะทำตามลำดับนี้อัตโนมัติ
  1) ยกเลิก Session ทั้งหมดของผู้ใช้คนนั้นทันที ไม่ให้ Login แบบเดิมได้อีก
  2) ปิดการใช้งาน Supabase Account (ไม่ลบ เพื่อเก็บประวัติไว้)
  3) สร้าง record ใหม่ในตาราง external_users
  4) ส่ง Email แจ้งผู้ใช้พร้อม Token/Link ใหม่สำหรับ Role ใหม่

กรณีที่ 2 — เปลี่ยน Approval/Guest ไปเป็น Administrator/Supervisor:
  1) ยกเลิก Token เก่าทันที ไม่ให้ใช้ Link เดิมได้อีก
  2) สร้าง Supabase Account ใหม่สำหรับผู้ใช้คนนั้น
  3) ส่ง Email ให้ผู้ใช้ตั้ง Password ด้วยตัวเอง (Admin ไม่รู้ Password)
  4) อัปเดตประวัติใน user_registry

หลักการสำคัญ:
  ห้ามลบ record เก่าเด็ดขาด เพราะจะทำให้ประวัติการทำงานหายไป
  ให้ปิดการใช้งาน (Disable) เท่านั้น เพื่อรักษา Audit Trail ไว้ครบ

=======================================================
ส่วนที่ 9: ข้อจำกัดจำนวน User
=======================================================

ระบบมีการควบคุมจำนวน User ไว้ดังนี้:
  จำนวน User สูงสุดในระบบ : 50 คน
  จำนวนที่สร้างได้ต่อวัน  : ไม่เกิน 5 คน
  จำนวนที่สร้างได้ต่อเดือน: ไม่เกิน 10 คน

เมื่อ Admin กดสร้าง User ใหม่ ระบบจะตรวจสอบตัวเลขเหล่านี้ก่อนทุกครั้ง
ถ้าเกินจะแสดง Error และไม่อนุญาตให้สร้างต่อ

=======================================================
หมายเหตุสำคัญ
=======================================================

- Service Role Key ที่ใช้สร้าง/จัดการ User ต้องเก็บไว้ที่ Server เท่านั้น
  ห้าม expose ไปที่ Browser เด็ดขาด (ตรวจสอบว่าไม่ได้ขึ้นต้นด้วย NEXT_PUBLIC_)

- PIN ที่บันทึกลงฐานข้อมูลเป็น Hash เสมอ ไม่มีการเก็บ PIN จริงๆ
  แม้แต่ Admin ก็ไม่รู้ PIN ของผู้ใช้คนอื่น

- ผู้ใช้ที่ถูก Disable จะถูกเก็บข้อมูลไว้เสมอ ไม่มีการลบ
  เพื่อให้สามารถ Audit ย้อนหลังได้ว่าใครทำอะไรในระบบบ้าง

- ระบบ Email ที่ใช้เป็น Transactional Email ไม่ใช่ Bulk/Marketing
  จึงไม่มีความเสี่ยงถูกระบบ Spam กรอง เพราะส่งเฉพาะคนที่ถูก Assign เท่านั้น
